# Harpoon 2.0.0 release candidate (rc.3)

Status: [`v2.0.0-rc.3`](https://github.com/krazybean/Harpoon/releases/tag/v2.0.0-rc.3) is a published GitHub **testing
prerelease**, like rc.2. It is not stable `2.0.0`; `v0.1.1` remains the latest stable desktop release. Its purpose is
**compatibility**: it is the first release that can read a deployment journal after a Git registration or an
application has been removed (journal schema 2). Both removals stay **closed in every shipping build**; nothing in this
release writes schema 2. A later opt-in release may.

The published release notes on GitHub are authoritative for the release itself; this page records the same facts for
the repository.

## What rc.3 contains that rc.2 does not

- The schema-2 journal reader (`gitdrop` record, schema check): a build older than this cannot open an upgraded journal.
- Removal code that is implemented and tested, but not available (see
  [removal status](../results/DEPLOY_GIT_REGISTRATION_REMOVAL.md#status-what-is-implemented-and-what-a-shipping-build-can-do)).
  Application removal v1 applies only to never-deployed applications.
- The guest initramfs with the guest-DNS fix (#152), for the arm64 guest. The tree's arm64 initramfs and manifest changed on
  2026-11-02, after rc.2 (2026-10-30): that is why rc.2's recorded initramfs hash differs from this tree's.
- `harpoon version` reports the release version (it printed `0.1.0`).
- Release verification: `verify-bundle.sh` checks the bundle's journal reader and that no acceptance-only file is inside;
  `tools/release/macos/verify-release-assets.sh` fails a release whose DMG is not actually attached.

## Verified, and not verified

**Verified:** universal slices and `verify-bundle` (CI); the journal reader and capability checks on the built bundle (CI);
Developer ID signatures, notarization, stapling and Gatekeeper (above); and, on Apple Silicon, the runtime packaged in this
DMG, run in an isolated test namespace, booted its guest, reached Docker-ready and ran an Alpine container.

**Not verified:**

- **The shipping desktop was not installed or launched in acceptance.** Its sockets and lock files are shared with a running
  production engine, so a launch could not be isolated safely. The desktop UI, first launch, the shipped desktop's reading of
  a journal, and the observed closed state of the removal controls are covered only by build-time checks and CI tests.
- **Intel guest boot.** The Intel binaries are packaged and verified at the binary level; no Intel guest was booted and no
  Intel Mac was used.
- Upgrade from rc.2 or rc.1, a second Mac, repeated cold boots, a clean-machine install, and `harpoon doctor` in the
  acceptance environment.

## Compatibility and rollback

- rc.3 reads schema 1 and schema 2 and never writes schema 2.
- Once a removal is recorded (possible only in a later release that enables it), builds older than rc.3 cannot open that
  journal: they stop with `invalid SQLite record` and leave it unchanged. Move every installation that can open the journal to
  rc.3 or later first.
- Moving from rc.3 back to rc.2 has **not** been tested. Keep a copy of your Harpoon data directories before trying a
  prerelease.

## Known differences and limits

- **The x86_64 guest is older than the arm64 guest.** The arm64 initramfs is built in-tree (reproducible). The x86_64
  initramfs, kernel and both root images come from the published guest-assets tarball (`guest-assets-23ea679e362b`, built
  2026-10-20), which predates the guest-DNS fix. Rebuilding it needs Virtualization.framework, which hosted CI does not
  provide. Intel remains experimental.
- Intermittent `VZErrorDomain 1` failures when starting a virtual machine are a known Virtualization.framework limitation of
  the host; they have been characterized, not fixed.
- rc.3 is Developer ID signed and notarized, so Gatekeeper is expected to open it without an override; do not disable
  Gatekeeper globally. (rc.2 has no downloadable assets, and earlier prereleases are ad-hoc signed.)
- The remaining 2.0 gates (clean second-Mac acceptance, 2×30 cold boots, upgrade/rollback with state preserved, desktop
  install and first-launch acceptance) are open; see [rc.2](v2.0.0-rc.md#remaining-gates). Developer ID signing,
  notarization and Gatekeeper assessment, listed there, are done for rc.3.
