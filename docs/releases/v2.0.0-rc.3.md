# Harpoon 2.0.0 release candidate (rc.3)

Status: `v2.0.0-rc.3` is a testing prerelease, like rc.2. It is not stable `2.0.0`; `v0.1.1` remains the latest stable
desktop release. Its purpose is **compatibility**: it is the first release that can read a deployment journal after a
Git registration or an application has been removed (journal schema 2). Both removals stay **closed in every shipping
build**; nothing in this release writes schema 2. A later opt-in release may.

## What rc.3 contains that rc.2 does not

- The schema-2 journal reader (`gitdrop` record, schema check): a build older than this cannot open an upgraded journal.
- Removal code that is implemented, tested and accepted in a disposable desktop, but not available (see
  [removal status](../results/DEPLOY_GIT_REGISTRATION_REMOVAL.md#status-what-is-implemented-and-what-a-shipping-build-can-do)).
- The guest initramfs with the guest-DNS fix (#152). The tree's arm64 initramfs and manifest changed on 2026-11-02, after
  rc.2 (2026-10-30): that is why rc.2's recorded initramfs hash differs from this tree's. Both are internally
  consistent (each manifest equals its file's hash).
- `harpoon version` reports the release version (it printed `0.1.0`).
- Release verification: `verify-bundle.sh` checks the bundle's journal reader and that no acceptance-only file is inside;
  `tools/release/macos/verify-release-assets.sh` fails a release whose DMG is not actually attached.

## Provenance: nothing is copied from notes

No checksum is written into these notes ahead of time. The DMG's SHA-256 is taken from the artifact itself:

1. The `Universal macOS DMG` workflow builds the DMG and records, in its run summary and in a `SHA256SUMS` file uploaded
   with the artifact, the DMG's SHA-256 and size, the source commit, the app and runtime versions (which must equal
   `package.json`), and both guest manifests as shipped.
2. The release script (`tools/release/macos/release.sh`) recomputes the SHA-256 after signing and notarization and writes
   it to `SHA256SUMS` and `RELEASE-PROVENANCE.txt`.
3. After uploading, `verify-release-assets.sh vX.Y.Z <dmg>` must pass: the release has the asset, uploaded, of the same
   size and SHA-256. A release is not distributed until it does.

## Known differences and limits

- **The x86_64 guest is older than the arm64 guest.** The arm64 initramfs is built in-tree (reproducible). The x86_64
  initramfs, kernel and both root images come from the published guest-assets tarball (`guest-assets-23ea679e362b`, built
  2026-10-20), which predates the guest-DNS fix. The Intel guest therefore does not have it. Rebuilding it needs
  Virtualization.framework, which hosted CI does not provide.
- The Intel build has not been live-booted on an Intel Mac.
- Unless the release is signed and notarized with the Developer ID configuration, it is ad-hoc signed and Gatekeeper
  rejects it at first launch; use the contextual **Open** action, and do not disable Gatekeeper globally.
- The remaining 2.0 gates (clean second-Mac acceptance, 2×30 cold boots, upgrade/rollback with state preserved,
  Gatekeeper-assessed notarized release) are unchanged from [rc.2](v2.0.0-rc.md#remaining-gates) and are not claimed.
