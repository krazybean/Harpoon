# Harpoon 2.0.0-rc.4 (testing prerelease)

Status: [`v2.0.0-rc.4`](https://github.com/krazybean/Harpoon/releases/tag/v2.0.0-rc.4) is a published GitHub **testing prerelease**. The published release notes are authoritative; this page records the same facts for the repository.


> **Testing prerelease, not stable 2.0.0.** `v0.1.1` remains the latest stable desktop release. The packaged Apple Silicon runtime passed an isolated boot, container and hard-stop recovery acceptance. The shipping desktop app was **not** launched or installed in acceptance, Intel guest boot is **unverified**, and the two-Mac 60-cycle startup reliability gate is **still open**. Use disposable containers and keep a copy of `~/Library/Application Support/Harpoon` and `~/Library/Application Support/com.harpoon.desktop` before trying a prerelease.

- **`Harpoon-2.0.0-rc.4-universal.dmg`**: universal (Intel x86_64 + Apple Silicon arm64), 359,820,098 bytes
- **SHA-256:** `7dd7cbf2a190f192a886419b1ee84cf38c34ad9f557d0d7c9af8a55e45608d51` (also in `SHA256SUMS`). This is the hash of the final, notarized and stapled file and the only checksum to verify.


Requires macOS 12 or later. The image is signed with a Developer ID, notarized by Apple and stapled, so Gatekeeper opens it without an override. Do not disable Gatekeeper.

### What changed since rc.3

- **Lifecycle recovery (#207).**
  - Docker now starts again after a hard stop of the engine or host. A stale containerd PID file on the persistent guest disk could collide with a live PID and fail the next start; the guest init removes it at boot.
  - A release confirmed serving is set to restart policy `unless-stopped`, after its success is durable in the journal. Candidates, failed releases and releases stopped on purpose stay down.
  - `harpoon-deploy restart-policy` (dry run by default) applies the same to releases that predate this. Existing applications stay at policy `no` until it is applied.
  - A second engine on an occupied runtime namespace is rejected before any VM work.
- **Source deployments and the deployment workspace (#205):** generated build recipes for npm and Python projects, Metrics, release-aware cleanup, and the redesigned Overview and Settings.
- **Disk and startup:** 4 GiB default root disk with user-confirmed expansion and space reclamation (#191, #193), bounded guest console storage and host-wide memory admission (#203), a dead guest is not Docker-ready (#196), and desktop startup cannot hang on a slow step (#195).
- **Build (#206):** host proc-macro dylibs are kept unstripped so Xcode 27's linker output loads.
- **Guest assets:** both guest initramfs files include the DNS fix and the PID-file fix.
  - arm64 sha256 `6fae89f2960c49bdfd1f3d3aa17b5cb7165262f50fc07ae296a269c6bdadde50`
  - x86_64 sha256 `f33320b53c02bc81da7783a000d4b3e77997e8cdc8e1f82eecfaa4161cc87c75`
- The journal reader is unchanged from rc.3: it reads schema 1 and 2 and never writes schema 2. Removal stays closed in every shipping build.

**Not verified**

- **The two-Mac, 60-cycle startup reliability gate is open.** It has not been run and is not waived.
- **The shipping desktop app was not installed or launched in acceptance** (its sockets and locks are shared with a running production engine). A source deployment through the shipped desktop, including its health check and recovery, was not run on this bundle; those paths are covered by CI tests against a fake Docker, and the restart behavior was measured on a disposable VM.
- **Intel guest boot is unverified.** The x86_64 slices and the rebuilt Intel initramfs verify at the binary and archive level only; no Intel guest was booted and no Intel Mac was used.
- **Clean-install and upgrade/rollback are incomplete.** Upgrade from rc.3 or earlier, and moving back, were not tested.
- **Intermittent guest faults are unresolved.** `VZErrorDomain 1` failures when starting a VM and occasional guest crashes under Virtualization.framework have been characterized, not fixed.

### Known limits

- Existing application containers keep restart policy `no` until `harpoon-deploy restart-policy --apply` is run with the live-change authorization.
- `tools/guest-builder/verify-guest.sh` has a stale "default 32G" check (the default became 4 GiB in #191); it fails for both architectures and is unrelated to the shipped assets.
- This is a prerelease: expect rough edges and report them.
