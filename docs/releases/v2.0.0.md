# Harpoon 2.0.0

Status: **release preparation. Not tagged, signed, notarized or published.** This page is the draft of the 2.0.0 release notes.
The mandatory gates listed under [Release gates](#release-gates) are open; nothing here is a claim that they passed.

## Supported platforms

| Platform | Status |
|---|---|
| Apple Silicon Mac, ARM64 Linux guest, macOS 12 or later | **Supported. The 2.0.0 release target.** Tested only on the development Mac (M3 Pro, 18 GiB, macOS 27.0.1); other Macs and macOS versions are unverified. |
| Intel Mac (x86_64) | **Experimental, not supported.** The universal DMG packages x86_64 binaries and an x86_64 guest, but no Intel guest has been booted and no Intel Mac used. The x86_64 guest comes from an older guest-assets tarball and lacks the guest-DNS fix and the corrected init idle loop. |
| Windows and Linux hosts | **Unsupported.** |

Podman/rootless is experimental and not part of the 2.0 compatibility matrix.

## Changes since 2.0.0-rc.3

The full, per-change list is in [unreleased.md](unreleased.md) (it becomes this release's change log). The two large items:

- **#196, a dead guest is not Docker-ready.** `harpoon status` counts Docker as ready only when `GET /_ping` is answered through the socket.
  After three vsock connect failures the bridges stop calling Virtualization.framework and probe once every 15 s. A guest kernel panic is
  detected from the console and reported as `guest_panic`; nothing is restarted or stopped.
- **#203, host-resource safeguards.** Found after a guest console flood exhausted the host:
  - The serial console is read from a pipe and kept in a rotating two-file log of at most 8 MiB, written at a limited rate. A flood is
    drained and counted; a healthy guest is never stopped for being noisy.
  - Starting a guest reserves its memory plus 512 MiB in a host-wide registry. The total may not exceed 60% of physical RAM, otherwise the
    start is refused with exit code 11 and the numbers.
  - The guest init idle loop no longer spins if `sleep` fails. The arm64 initramfs in this release contains the corrected loop.
  - VM-backed test scripts run under a deadline, watchdog and exact-ownership guard (test tooling only; production VM uptime is not limited).
- Also included: 4 GiB default for **new** root disks with an offered expansion, disk reclaim, a desktop that follows external
  stop/start, and bridge connection ownership fixes. See [unreleased.md](unreleased.md).

## Verified

Final single-VM reliability gate, 2026-11-13, on the development Mac, using a runtime built from `main` at `341332d` and the shipping
arm64 guest assets (initramfs `58420573…`, kernel `d625d13a…`), in a private test namespace under an independent deadline guard and watchdog:

- Configuration: 2 vCPUs, 4096 MiB guest RAM, 4 GiB root disk. Host memory pressure level 1 before the start, no active swap-outs, 35 GiB free disk.
- Boot: Docker ready at +17.4 s and management ready at +18.4 s.
- Soak: 601 s after readiness. Nine low-frequency Docker management operations (version, ps, images, info, system df) all succeeded and
  `harpoon status` stayed running and Docker-ready after each. 300 guest heartbeats were recorded (one per 2 s) with no gap of 30 s or more.
- No `Illegal instruction`, SIGSEGV, init kill, kernel panic or `HARPOON_INIT_SLEEP_FAILED`. The serial log reached 36 KB, with no rotation or overflow.
- Resources: host memory pressure never exceeded level 2, swap-outs did not change, free disk stayed at 35 GiB. The engine used at most 53 MiB.
- Teardown: `harpoon stop` took 2.3 s; the engine and the Virtualization helper exited and no process or test directory remained.
- Result: **17 of 17 recorded checks passed.** This is one run.

Earlier on the same code: an offline regression for each safeguard, and hosted `validate` runs on #196 and #203.

## Known issue: unexplained intermittent guest faults

During development, two guests failed with userland crashes that have no identified cause:

- One guest began failing about 2.5–3 minutes after boot. Every `sleep` executed by the init loop died of SIGILL, and the idle loop turned that
  into a console flood (the incident that led to the #203 safeguards).
- Another guest's PID 1 died of SIGSEGV 87.6 s after boot, and the kernel panicked (`Attempted to kill init!`).
- The guests' root filesystem contents were identical to those of guests that ran normally. The investigation did not find a cause in the
  guest userland, kernel or image, and it found no evidence on guest memory.
- **Frequency is unknown.** Neither a rate nor a trigger has been established, and none is claimed. The final reliability gate above ran
  clean; one clean run does not show the fault is gone.

What 2.0.0 does about it: a guest panic is detected and reported, an init `sleep` failure no longer floods the host, and a guest console can no longer
exhaust host memory or disk. What it does not do: prevent the fault, restart the guest, or explain it. If it recurs, `harpoon status --json` reports
`guest_panic` or the serial log carries `HARPOON_INIT_SLEEP_FAILED`; please report it with `harpoon diagnostics`.

## Known limits

- Intermittent `VZErrorDomain 1` failures when starting a virtual machine are a known Virtualization.framework limitation of the host; they
  have been characterized, not fixed. Startup retries are bounded.
- The 4 GiB new-disk default has had one recorded live boot; some workloads need more (`harpoon disk expand`, or `HARPOON_DISK_SIZE`).
- Live deployment, replacement and rollback open only for attended use behind explicit confirmation; unattended execution, registration removal and
  application removal remain closed (see the roadmap).
- Long-term stability is unproven: the evidence is a 10-minute soak on one Mac, not days of uptime, container workloads or memory pressure.

### Proposed waiver (needs the owner's explicit approval; not granted)

- **Waive:** the full two-Mac, 60-cycle cold-boot requirement of the [startup reliability gate](v2.0.0-startup-reliability.md).
- **Replace with:** 10 cold start/stop cycles on the clean-install machine, running the signed DMG, with the per-cycle evidence and the failure
  recovery rules from that document unchanged (any cleanup or recovery failure is a FAIL), in addition to the reliability run above.
- **Why:** the risk those cycles measure (`VZErrorDomain 1`) is already documented as characterized and unfixed, so 60 cycles would add a
  sample, not a fix, and the second Mac is not available.
- **Residual risk the release notes must keep:** startup reliability is evidenced by one Mac and a small sample, with no statistical guarantee.

### Minimal checks proposed for upgrade, rollback and Docker contexts

Run on the clean-install machine, on a copy of the data directory (back it up first):

1. **Upgrade.** Install the rc.3 DMG, start, run `docker run --rm alpine:3.20 echo OK`, create a named volume holding a marker file, stop. Install 2.0.0 over it.
   Pass: Harpoon starts, the volume marker and the pulled image survive, `harpoon doctor` reports no failure.
2. **Rollback.** Stop 2.0.0, restore the backed-up data directory, reinstall rc.3. Pass: rc.3 starts and Docker is ready. 2.0.0 does not write
   journal schema 2, so rc.3 should read what 2.0.0 left; the check confirms it.
3. **Docker context.** `docker context ls` shows the `harpoon` context; `docker --context harpoon version` answers. Leave a stale socket file at Harpoon's
   socket path with Harpoon stopped; `harpoon start` must recover. The duplicate-endpoint and authentication-required cases stay covered by the
   offline discovery fixtures only, and Docker Desktop is not exercised. The notes must say so.
