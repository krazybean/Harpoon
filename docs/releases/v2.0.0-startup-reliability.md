# Harpoon 2.0 startup reliability gate

Status: specification only. This document does not start or stop a VM.

## Scope and safety

The gate is for the Apple Silicon 2.0 target and must run against a disposable
test runtime. Do not use storage-pressure experiments, modify persistent images,
or delete user Docker state. Podman/rootless is not a 2.0 requirement.
Intel/universal, Windows/Linux hosts, and the proposed deployment control plane
are post-2.0 work.

Before the run, record the exact Harpoon commit, app/runtime hashes, macOS
version, hardware model, architecture, available disk, and test-disk identity.
Use a copied test disk and stop if its identity changes.

## Required run

Run 30 cold start/stop cycles on each of two Apple Silicon Macs. A cold cycle
means the runtime is stopped, its owned ephemeral sockets and lock are absent,
and the test disk remains attached but unmodified between cycles.

For every cycle, capture the UTC timestamp, host model, macOS version, free disk
(`df`), exact commit/hash, command exit status, bounded structured VZ
diagnostic, `harpoon status --json` before/after start and stop, Docker readiness,
and whether the UI remained actionable.

After any failed start, require all of the following before continuing:

1. status reports stopped;
2. no Harpoon-owned stale lock or socket remains;
3. the structured VZ diagnostic is saved;
4. one bounded retry starts successfully; and
5. the UI reports an actionable failure or recovery state rather than hanging.

If cleanup or recovery fails, stop the run and classify the gate as FAIL. Do
not silently retry until the count looks healthy.

## Reporting and release interpretation

Report every cycle and every failure. Do not manufacture `60/60`, and do not
claim a statistical guarantee from this sample. A clean run is evidence for
the release gate only when both Macs complete all 30 cycles and all cleanup and
recovery criteria pass. Every failure remains visible in the release notes with
its host, disk headroom, diagnostic, and recovery result.

The unresolved host/Virtualization.framework failure mode remains a release
risk even after a clean sample. Release notes must distinguish observed
evidence from an absence of observed failures.

## Release checklist

- [ ] exact feature-branch SHA recorded;
- [ ] guest kernel/initramfs/root provenance and SHA checks pass;
- [ ] release preflight passes on a clean tree before signing;
- [ ] codesign, DMG signature, notarization, and Gatekeeper failures are
      fail-closed;
- [ ] Mac A: 30/30 cycles with complete evidence;
- [ ] Mac B: 30/30 cycles with complete evidence;
- [ ] no cleanup/recovery failure and no unreported cycle;
- [ ] Docker Desktop, Harpoon, stale-socket, duplicate-endpoint, and
      auth-required context cases are recorded; Podman/rootless is explicitly
      out of the 2.0 gate;
- [ ] persistent-disk upgrade/rollback evidence is run on a disk copy;
- [ ] Developer ID signing/notarization and publication are separately
      approved; no tag or release is created by this Step 1 session.
