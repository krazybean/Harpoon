## Phase 2 — Ponytail review (lazy senior dev)

Applied ladder after tracing `VMManager` → `Bridges` → `virtio_balloon` → `Spike5` → `m13-test.sh`.

**1. Does this need to be built at all?** YES — product goal is low post-workload resident memory, not just low configured memory. Spike5 shows 919 MB retained after workload (no natural drop), so need exists (YAGNI not triggered).

**2. Does it already exist?** Balloon device and control already exist (PROVEN), but no automatic policy. Reuse `VZVirtioTraditionalMemoryBalloonDevice` and `/tmp/harpoon-control`, do not invent new transport.

**3-5. Stdlib / platform / dependency?** `VZVirtioTraditionalMemoryBalloonDevice` is native Apple primitive; no stdlib or dependency solves host-visible reclamation.

**6. Can this be one line?** No — need policy, but smallest is one bounded balloon request, not full engine.

**Challenges:**
- **Ballooning correct first optimization?** CHALLENGED — Spike5 guest `815→555→806 MiB` PASS but host `507→604→627 MB` **NOT OBSERVED** on `macOS 26` `Virtualization 1112.1.16`. Balloon alone did not reduce host `phys_footprint` on this platform under pressure (maybe need host pressure or longer wait). Yet it's the only Apple-supported primitive proven configured, so it's the smallest experiment — but expect host may still not drop.
- **VM already naturally returns memory?** NO — Spike5 high-water `919` retained +60s, no natural drop. Demand-backed growth proven, not return.
- **Measurements host-resident?** MUST be `ps -o rss` Harpoon + VM XPC `lsof -F disk` combined, or `footprint -p` `phys_footprint`, not guest `MemAvailable`/`free`/`cgroup`/`configured`. Harness does host RSS via `ps`+`lsof`, not guest free.
- **Page cache untouched?** YES — `memory-model.md` downgrades `drop_caches` to EXPERIMENTAL. **Explicitly challenge `echo 3 > /proc/sys/vm/drop_caches`**: Linux page cache is valuable; destroying it without proof trades guest performance (Node, Git) for host number. Do NOT add to normal runtime. Spike5 pending three-way (balloon vs drop vs both) not proven.
- **Guest cooperation required?** YES — `virtio_balloon.ko` required and proven, but host reduction still not observed, so cooperation not sufficient alone; host pressure or timing may matter.
- **Oscillation/stall risk?** Policy must have hysteresis (grow/reclaim thresholds, dead zone), rate limiting, cooldown after each adjust, never exceed guest safe availability, respect headroom. One-shot bounded request avoids oscillation.

**Rejected:** `drop_caches` in normal runtime, combined balloon+cache+resize+sysctl in same experiment, VM resizing, guest sysctl tuning. **Chosen:** One isolated balloon inflation after workload release (see Phase 5).

**Ponytail simplification:** No `harpoon memory` CLI yet — `ponytail: manual `echo 768 | nc -U /tmp/harpoon-control` with log markers is sufficient for one-shot experiment; full policy engine with hysteresis is future.

### Required conclusions (repository evidence)

- **Natural VZ reclamation is PROVEN host-visible:** `512` `103872 idle → 103568 release-60` (−304), `768` `389056 → 96816` (−292240), `1024` `374544 → 99696` (−274848); transient spike `189568/200448/217360` at `release-immediate` falls `~50%` by `+60s`.

- **Configured 512/768/1024 capacity does not imply equivalent idle RSS:** idle `103872` vs `389056` vs `374544` — 512 idle is `~3.7×` smaller than 768/1024 idle; larger configured does not force larger resident.
- **One-shot balloon does NOT demonstrate consistent material advantage over natural:** `512` natural `126960/103568` vs balloon `101568/116960` and rerun `123200/114032` — `+30s` sometimes lower, `+60s` higher; `768` natural `97760/96816` vs balloon `116592/102592` and rerun `110000/94288` — balloon sometimes *higher*. - **Keep existing balloon control as EXPERIMENTAL/manual:** device + `/tmp/harpoon-control` + driver remain PROVEN, single `echo $target | nc -U` stays for experiments, not production policy.
