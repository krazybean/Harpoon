# Bounded cutover recovery — offline slice

Status: implemented and tested **offline only**. Live replacement is not enabled; the shipping gate
(`Gate::shipping()`) is unchanged and closed. No Docker or VM was contacted. Not production readiness.
Explicit rollback of a completed deployment is the next milestone and is not part of this slice.

## What exists

| Requirement | Implementation | Evidence |
|---|---|---|
| Pin the immutable, non-secret configuration of a release | `ReleaseConfig` (`deploy/src/release.rs`): exact image id (`sha256:…`, a tag is rejected), tag for display, container and host port, health spec, memory/CPU/PIDs limits. Stored in the deployment snapshot (`Deployment.pinned`), set before the final check, appended to the snapshot only when present so older snapshots decode unchanged. No environment values, no secrets; the per-container response marker is regenerated for every container | `deploy/tests/b11_recovery.rs`, `deploy-journal/tests/sqlite.rs`, unit test in `release.rs` |
| Restore after a failed confirmed cutover | `Run::restore_phase` calls `Backend::restore_previous(io, previous, budget)` once. The Docker backend re-checks the pinned image id and the previous release's labels, serves on the previous release's still-held lease, creates a new container (ledger intent → create → receipt, disposition `Retain`) from the pinned image id with the pinned limits and port, starts it and runs the **pinned** health check | `deploy-docker/tests/b11_recovery.rs` (fake Docker) |
| One bounded attempt, default 60 s | `Policy.restore_budget_ms` (60 000); the backend limits every call to the remaining budget; the engine treats a result that arrives past the budget as unverified (`restored_unverified`) and a backend timeout as `restore_failed(timeout)`. No retry exists | tests: budget passed through, late answers, 1 ms budget against a slow Docker, one `start` request only |
| Exact outcome, persisted and reported | `restored`, `restored_unverified`, `restore_failed(reason)`, `not_attempted(reason)` with reasons `config_unavailable`, `image_missing`, `docker_unreachable`, `timeout`, `start_failed`, `interrupted`. Recorded as `InProgress` **before** the backend is called, then final; printed by `deploy`/`replace`/`restore` and `status` | engine, Docker and CLI tests |
| Measured interruption and restoration duration | `Deployment.interruption` (stop → restored/confirmed) and `Recovery.started_ms/finished_ms`; shown in `status` and by the commands. Simulated runs say "simulated clock" | engine (1 500 ms and 500 ms from scripted timings), CLI |
| Pause triggers only after a real failed cutover | `trigger_pauses(deployments)` is derived from the durable records: a cutover that failed, or began and never finished. Build, preliminary-check and unconfirmed-plan outcomes never pause. Shown in `status`. There is no automatic trigger yet, and no `resume` | engine + CLI tests |
| Preserve the failed candidate; touch nothing else | new `EndState::FailedCutover`: the candidate's `RemoveOnFailure` container and lease are kept (stopped) with its retained image and logs; temporary preliminary resources are still removed. The previous release's container only ever receives `stop` (verified by id, name and all three labels); unrelated applications, unlabelled containers, volumes, networks are never named in a request | Docker tests inspect every request |
| Crash during cutover or restoration | `recover_on_start` marks the deployment `Interrupted`, never resumes, closes an unfinished restoration as `restore_failed(interrupted)`, and `application_may_be_down()` stays true. `restore --deployment ID [--apply]` (simulate only) makes the explicit attempt: allowed once, only for an interrupted deployment whose cutover began and which has no recorded attempt (even an unfinished one forbids another). The store accepts exactly this change to an `Interrupted` deployment (none → in progress → one final outcome) and rejects any other, failing closed | crash sweeps at every write (engine and Docker), `replay` tests, SQLite restart test, CLI tests |
| SQLite durability, record-before-side-effect, ownership, fail closed | snapshot of the attempt is written before restoration starts; all created objects go through the ledger; removal and stop re-verify labels; damaged or inconsistent records make every command exit 4 | existing suites plus the above |

## Boundaries kept

* `DockerConfig.enable_replacement` is `false` by default, is never set by the CLI, and `DockerBackend::supports_cutover()` returns it. Against a real Engine the engine therefore still stops after the preliminary check.
* `replace` and `restore` refuse without `--simulate`, before anything is read.
* No automatic rollback of a completed deployment; no zero-downtime proxy, secrets, Git, UI or daemon.

## Hardening (follow-up PR)

Three limitations listed here after PR #126 were fixed. This is hardening of B11, not a new mechanism; the one-attempt guarantees are unchanged and live replacement is still disabled.

| Limitation | Fix | Evidence |
|---|---|---|
| A restored container belonged to the failed deployment's ledger and nothing knew it served | `Deployment.replaces` records the release a cutover replaces, in the write that begins the cutover. `serving_release()` (`deploy/src/serving.rs`) derives, from the durable records, which release an application serves and **which container** serves it (the release's own, or `hp-<failed>-restored` recorded under the deployment that restored it); a later success supersedes a restoration, a restoration supersedes an older success. `replace` passes that container to the backend, whose `stop_current` verifies and stops exactly it (id, name, all three labels). `status` prints `serving:`. `teardown --deployment R` handles R's own container **and** any container a restoration made for R, each under its own recorded deployment, and still never touches the failed candidate. `reconcile` removes the failed candidate and keeps the restored container (`Retain`). A candidate's lease is no longer held back by the restored container | `deploy/tests/b12_hardening.rs`, `deploy-docker/tests/b11_recovery.rs` (second replacement stops the restored container, not the old one), `deploy-cli/tests/b12` (status, replace, teardown, reconcile) |
| The pin was saved after the new container started | New `Backend::plan_release` reserves the port lease through the ledger and returns the configuration **before** anything is created or stopped; the engine pins it and saves it, then records `replaces`, then begins the cutover. A plan that cannot be made fails the deployment with nothing stopped (no pause). After `start_new` the actual configuration is compared with the plan; a port collision that moved the release is re-pinned immediately. A restoration also refuses (`not_attempted(config_unavailable)`) when the pinned port is not a port the previous release leased, instead of trusting it. The plan now warns, before confirmation, when the release being replaced has no pin. Snapshots stay compatible: the pin and `replaces` are optional trailing fields, written only when set, so pre-existing and PR #126 records decode unchanged | crash sweeps at every write in the engine and against the fake Docker (a container or a stop/start exists only if the pin was durable first), snapshot-shape tests, collision test |
| The failed candidate could hold the port when the process died mid-cutover | New read-only `Backend::restore_blockers`. The Docker backend lists containers and reports every **running** container that publishes the previous release's port (excluding the previous release's own recorded container), classified by label ownership: this application's (suggests `reconcile`, which removes it only after verifying ownership), another application's, or unlabelled (never touched, "free the port yourself"). Stopped containers that merely have the port configured do not bind it and are only logged. In the automatic path a blocker makes the outcome `not_attempted(port_in_use)` and nothing is created. In the explicit path the check runs **before** anything is recorded, so the command reports the problem and **does not spend the one attempt**; after the port is cleared the single attempt can be made. Eligibility (interrupted, cutover began, no recorded attempt) is checked first, so a repeat is still refused without contacting Docker. The deployment must also record which release it replaced, and `restore` uses that record instead of guessing | engine tests (blocked automatic and explicit), Docker tests (three owner classes, nothing changed, then restored once), CLI tests |

## Remaining limitations

* **Live behaviour is unproven.** Every Docker test uses a simulated server. Real container stop/start semantics, port release timing and the forwarder's sync lag (up to 10 s) are untested, and the measured interruption has no live value.
* **Pin timing, residual.** The plan is pinned before any side effect, but if a port collision moves the release the corrected pin is written just after the second container starts. A crash in that window leaves a pin whose port differs from the lease; a later restoration then reports `not_attempted(config_unavailable)` instead of using it. Releases deployed before pinning have no pin and say so in the plan.
* **Blocker detection reads one listing.** A container that starts publishing the port between the check and the restore is caught only by Docker's own start error (`restore_failed`). A host process (or the forwarder's lagging listener) on the port is not treated as a blocker.
* **A blocked explicit restoration is only reported.** Clearing the port is left to the developer (`reconcile`, or freeing it); the CLI has no simulated way to script a blocker, so that report path is covered by the engine and Docker tests.
* **Teardown of a restored release is supported; teardown by the failed deployment's id is not** (it is not a succeeded deployment): the failed candidate is removed by `reconcile`.
* **Pause has no consumer and no `resume`.** It is derived and shown; clearing it is a later milestone.
* **The prepared-candidate handoff is not solved**: a confirmed `replace` still rebuilds (see B10).
* A restoration cannot restore data, volumes or schema; it recreates the container only.

## Evidence needed before live replacement is enabled

1. A live run on a disposable application: replacement succeeds, with the measured interruption and the real port-forwarder lag recorded.
2. A live forced cutover failure (candidate fails its final check): restoration returns `restored` with its own health check, the previous image/configuration are the pinned ones, the failed candidate is kept, and `status` reports the restored container as serving.
3. Live `restore_failed` / `not_attempted` cases (image removed, port taken by a running container) behave as recorded, without touching any other resource; exact inventory restored afterwards (the B8.3 standard).
4. A live kill of `deploy` during the cutover and during the restoration, followed by `recover`, `status`, clearing any port holder with `reconcile`, and the explicit `restore` exactly once.
5. A live second replacement after a restoration, confirming the restored container is the one stopped, and a live `teardown` of a restored release.
6. Explicit written authorization for each live step, with the shipping gate still opened only in a separately built, separately authorized binary.
