## 2 Method (paired, 5 cycles)

- For each cycle 1..5:
  1. `harpoon/build/harpoon stop` (clean stale `PID 74135`), `pkill` spike1, sleep 2, verify `lockHeld false` `sockExists false` via `harpoon status --json`, record `VZ configuration validation` (both `validate OK`/`config validated`).
  2. Record start timestamp, attempt **minimal** once: `spike1/build/harpoon-spike1 spike1/cache/Image-virt harpoon/cache/harpoon-m4-initramfs.cpio.gz 15` (internal 15s timeout, no external `timeout`), record SUCCESS (`BOOT_DETECTED HARPOON_SPIKE_OK` + `SHUTDOWN_OK` in `/tmp/r1_logs/minimal_cycleN.log`) or full VZ error chain (`start failed: domain=VZErrorDomain code=1 info=[NSLocalizedFailure...]`).
  3. Wait 5s.
  4. Attempt **full** once: `harpoon/build/harpoon start` (single attempt, no retry beyond one per sample), record SUCCESS (`state running` + `dockerReady true` in `status --json`) or `VZErrorDomain 1` (`HOST_VZ_START_FAILURE` in `/tmp/harpoon-runtime/harpoon.log` + `start FAIL VZErrorDomain 1`), measure `elapsed_ms`, `vz_domain`/`vz_code`/`detail`.
  5. If success, `harpoon stop` cleanly; wait 5s; run other variant next cycle.

Output CSV: `timestamp,cycle,variant,result,elapsed_ms,vz_domain,vz_code,detail` at `/tmp/r1_paired.csv` (preserved below). Logs per variant at `/tmp/r1_logs/minimal_cycleN.log` + `full_cycleN.log` + `full_harpoon_log_cycleN.txt` + `host_info.txt`.

No kernel args changed, no kernel/initramfs/root replace, no broad `/tmp/harpoon*` delete, no reboot, no Sources modify.

## 4 Interpretation (per acceptance)

- **minimal FAIL + full FAIL in same host window: HOST/VZ STATE strongly implicated.** — **OBSERVED: 5/5 cycles both variants FAIL with identical `VZErrorDomain 1` `Internal Virtualization error` `The virtual machine failed to start.`** Minimal (no disk, no VirtioFS, no vsock, no balloon, 512M) and full (disk + 3 VirtioFS + vsock + balloon, 1024M) both fail in same 19:23Z window that also produced M18 `0/10` at 18:53 and M17 `17:57-18:21` consecutive. Same `Image-virt` `377d3480` and same `harpoon-m4-initramfs.cpio.gz` `70a89d` succeed historically when host healthy (`00:22:26`, `17:49`, `18:07` `BOOT_DETECTED`/`running` `16 PASS`), so not kernel/initramfs provenance.

- **minimal PASS + full FAIL repeatedly: HARPOON VM CONFIGURATION implicated.** — **NOT OBSERVED.** No cycle shows minimal PASS while full FAIL.

- **minimal PASS + full PASS: current blocked window cleared.** — **NOT OBSERVED in 19:23Z window** (0/10 PASS), but historically observed at `00:22`, `17:49`, `18:07` — so window is intermittent, not permanently blocked.

- **minimal FAIL + full PASS: investigate harness/provenance because unexpected.** — **NOT OBSERVED.**

**Conclusion:** Failures are not caused by Harpoon-specific devices/configuration (disk, VirtioFS 3 shares, vsock, balloon, VZNAT vs same NAT in minimal, 1024M vs 512M). Both topologies share only `Virtualization.framework`, `VZGenericPlatformConfiguration`, `VZLinuxBootLoader` `Image-virt` `console=hvc0`, `entropyDevices`, `serialPorts`, `networkDevices VZNAT`, `validate OK`. The error occurs after `validate OK` and `starting VM` before guest (`HARPOON_STATE BOOTING -> FAILED` before `HARPOON_DOCKER_READY`/`BOOT_DETECTED`, elapsed 2-3s). Therefore **HOST/VZ STATE strongly implicated** (host `Virtualization.framework` transient, not Harpoon topology). Harpoon device topology is **not implicated** in this window; device-by-device reduction not warranted now.

**Next experiment:** Device-by-device topology reduction **NOT needed** at this stage because minimal already fails. If future window shows minimal PASS + full FAIL, then next experiment is additive: start from minimal and add one device per run (disk, VirtioFS single share, vsock, balloon) to isolate.
