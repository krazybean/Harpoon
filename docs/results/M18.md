## 4 VZ startup reliability
**Addendum 2026-08-26 20:10 — Harness contamination fix (no Sources change):**
Prior M18 `HOST_VZ_START_FAILURE` results at `18:53:27-18:55:34` (0/10) and earlier `m18-test.sh` line 87 `grep -q "HOST_VZ_START_FAILURE" /tmp/harpoon-runtime/harpoon.log` searched the *entire persistent log* for historical entries. This caused a successful current VM start to be classified as `HOST_VZ_START_FAILURE` — evidenced by `m18-test.sh` reporting `BLOCKED HOST_VZ_START_FAILURE` while `harpoon status --json` immediately after showed `state=running` `dockerReady=true` `sockExists=true` `lockHeld=true` `pid=85916` (XPC 85917 alive) and `harpoon.log` continuously `HARPOON_PORT_VSOCK_CONNECTED`/`HARPOON_PORT_SYNC_RESULT containers=1`. The persistent log contained historical `HOST_VZ_START_FAILURE` from earlier blocked windows (17:57-18:55), so the full-log grep was stale-state contamination.
*Fix (harness-only, smallest trustworthy):* before each `harpoon start`, resolve authoritative log via `harpoon logs --path` and record byte size; after start, inspect *only bytes appended during that attempt* (handle truncation via `wc -c` and `tail -c +`); classification precedence (a) live `status --json state=running AND dockerReady=true AND docker --context harpoon version Server` → `START_PASS` (live outranks stale text), (b) else `VZErrorDomain 1`/`HOST_VZ` in CLI output or appended log → `HOST_VZ` for this attempt, (c) else distinct `RUNTIME_LOST`/`DOCKER_NOT_READY`. No log truncation, no broad `/tmp/harpoon*` delete. `check_runtime` and `wait_stable` and later 3× `vz reliability` now use `status --json state==running` not `grep -qi running` (fixes `not running` substring). `bash -n 0` `sh -n 0`. Ponytail: harness defect, not justification for retry daemon/signing/VM topology/new subsystem.
*Impact:* Prior 0/10 and earlier `m18-preserved-*` `HOST_VZ` classifications based on full-log grep are **contaminated and not valid startup evidence**; they are preserved as `m18-preserved-20260826-200856-contaminated`/`200905` for audit but must not be cited as current reliability. Current window at `20:08` was actually healthy (`running`/`dockerReady`/`vsock`), and the fixed harness will correctly classify `START_PASS` in healthy windows and genuine `HOST_VZ` (via appended log) in blocked windows (e.g., `20:09:11` genuine `HOST_VZ` with `stale` state, not running, appended log contains `HOST_VZ`).
